# 生产化路线图

把本项目从单机原型改造成**多用户平台**的工作清单。做完一项就勾掉一项；范围有变化时直接改这份文档。

最后更新：2026-10-12

## 前提假设

下面的计划按这四条假设写。任何一条不成立，对应阶段的范围要调整。

| 问题 | 当前假设 | 如果不是 |
|---|---|---|
| 用户是谁 | 内部员工 | 对外开放时，阶段二要升级到 Kata 或 Firecracker，阶段一要加租户概念 |
| 谁能上传 skill | 只有管理员 | 普通用户可上传时，阶段二要加审核流程和代码扫描 |
| 部署形态 | 先单机，后多副本 | 一直单机时，阶段四的队列和执行器拆分可以大幅简化 |
| 前端 | Gradio 只做调试，正式入口是 API | 要保留 Gradio 时，鉴权和文件接口要做两套 |

## 总览与执行顺序

阶段编号按主题划分，不等于执行顺序。有两块不依赖数据库和队列，可以提前做。

| 阶段 | 目标 | 依赖 | 状态 |
|---|---|---|---|
| 一 | 堵密钥泄露，加鉴权 | 无 | 代码已完成，待轮换 API Key |
| 二 | 沙箱隔离收尾 | 无 | 进行中（执行器重构已完成） |
| 三 | 状态外置到数据库和对象存储 | 一 | 未开始 |
| 四 | 队列化运行，执行器独立成服务 | 三 | 未开始 |
| 五 | 日志、测试、评测、部署 | 无，随各阶段推进 | 未开始 |
| 六 | 记忆机制 | 6.1 无；6.2 依赖三；6.3 依赖一、三 | 未开始 |
| 七 | 复杂任务执行（单 agent） | 7.1 依赖 6.1；7.2 依赖三、四 | 未开始 |
| 八 | 多 agent | 6.1、7.1，以及三里的 `SessionContext` 拆分 | 未开始 |

建议顺序：

1. 阶段一。风险最高，改动最小。（代码已完成，剩轮换 API Key）
2. 阶段二，同时做 6.1（上下文管理）和 7.1（预算与计划）。后两项做完，现有 agent 就能处理明显更长的任务。
3. 阶段三、阶段四。
4. 6.2、6.3、7.2。
5. 阶段八。
6. 阶段五里的评测集要早建：6.3、7.1、阶段八都要靠它判断改动是否有效。

## 阶段一：堵密钥泄露和入口

对任何人开放访问之前的最低要求。对应问题 1、2、3、4、10。

- [x] 从 `/run` 请求体和 Gradio 页面去掉 `api_base` 和 `api_key`
- [x] `model_id` 改为只能从服务端配置的白名单里选（`MODEL_ID` + `ALLOWED_MODELS`）
- [ ] **轮换 API Key**（需要在模型服务商那边手动操作；现有密钥只要服务被别人访问过就应视为已泄露）
- [x] 确定鉴权方式：先用服务端签发的静态 token（`core/auth.py`，只存哈希）。要换成 JWT 或公司统一登录时，替换 `authenticate()` 即可（**是否要换，待决定**）
- [x] API 加鉴权；Gradio 加登录
- [x] 会话 id 改由服务端生成，绑定用户，每次访问校验归属
- [x] skill 的安装和卸载只对管理员开放
- [x] 会话加空闲超时和每用户数量上限
- [x] 入口加限流，每用户限制并发运行数
- [x] 运行出错时不再把异常原文返回给调用方（可能带内部地址），改为返回错误编号，详情记日志

**完成标准**

- 未登录的请求全部被拒
- 用户 A 拿不到用户 B 的会话、文件和产物
- 页面源码和接口响应里搜不到密钥

- [ ] skill 镜像：安装 skill 时按 `requirements.txt` 构建专属镜像，运行时不装依赖
- [ ] skill 安装加固：限制压缩包大小、解压后总大小和文件数
- [ ] 禁止覆盖同名 skill，改为带版本号
- [ ] 新安装的 skill 默认是待审核状态，管理员发布后才可用
- [ ] workspace 用带容量上限的卷，把总量配额从事后检查改成硬限制
- [ ] 在 Linux 机器上验证 gVisor（`SANDBOX_RUNTIME=runsc`）和 workspace 的文件权限
- [ ] 默认配置改为启用沙箱，本机执行需要显式开启

**完成标准**

- 联网 skill 访问内网地址和元数据地址失败，访问公网成功
- 压缩炸弹和超大包被拒绝
- Linux 加 gVisor 下 `test_sandbox.py` 全部通过

## 阶段三：状态外置

做完这一步，服务重启不丢数据，也才具备多副本部署的条件。

- [ ] 引入 Postgres：用户、会话、消息、运行记录、skill 元数据
- [ ] 上传文件和产物改存对象存储（私有化部署可用 MinIO）
- [ ] 轨迹入库，按用户可查
- [ ] 拆分 `build_agent`：会话级资源（workspace、执行器、skill 注册表、用户身份、预算）放进 `SessionContext`，agent 级状态（模型连接、对话记忆、系统提示、工具列表）单独构建。阶段八也依赖这一项
- [ ] agent 改为每次运行时从库里的历史重建，不再长驻内存
- [ ] 数据库迁移工具和初始化脚本

**完成标准**

- 服务重启后，用户能继续之前的对话并下载之前的产物

## 阶段四：运行模型

把"一个请求一个线程"改成可排队、可取消、可多副本的运行方式。

- [ ] 任务队列加 worker，每次运行有独立 id，可查状态、可取消
- [ ] 同一会话加锁，防止并发请求同时操作一个 agent
- [ ] SSE 改为从事件流读取，支持断线重连
- [ ] 客户端断开后，运行可以继续或被取消，不再出现无人接收的后台线程
- [ ] 执行器拆成独立服务，API 进程不再持有 Docker 权限（新增一个 `SandboxExecutor` 的远程实现）
- [ ] API 补齐文件上传、产物下载、skill 管理接口（目前只有 Gradio 有）

**完成标准**

- 两个 API 副本同时运行，任意一个重启不影响进行中的任务

## 阶段六：记忆机制

**现状**：唯一的记忆是 smolagents 的 `agent.memory`，只在进程内存里，按会话隔离，重启即丢。多轮对话的历史（含每次脚本输出）原样累积，没有压缩。没有任何跨会话的记忆。

### 6.1 会话内的上下文管理

不依赖其他阶段，可以提前做。

- [ ] 旧轮次的工具输出只保留摘要或截断，完整内容留在 workspace，需要时用 `@r_xxx` 引用
- [ ] 历史超过阈值时，把较早的轮次压缩成一段摘要；已加载的 skill 正文和本轮上传的文件名不压缩
- [ ] 统计每次请求的上下文长度，接近模型上限前先压缩，而不是等接口报错

### 6.2 会话持久化

依赖阶段三。

- [ ] 消息和步骤入库，会话可在重启后恢复、可列出历史会话
- [ ] 恢复时用"摘要 + 最近若干轮"重建上下文，而不是回放全部历史

### 6.3 跨会话的用户记忆

依赖阶段一（用户身份）和阶段三（数据库）。

- [ ] 记忆条目表：按用户隔离，每条有类型（偏好 / 事实 / 常用做法）、内容、来源会话、时间
- [ ] 提供 `remember` 和 `recall` 两个工具；系统提示里只放该用户记忆的简短索引，正文按需读取（与 skill 的渐进加载同一思路）
- [ ] 先用关键词和类型检索；条目多到索引放不下时再加向量检索（pgvector）
- [ ] 用户可查看、修改、删除自己的全部记忆
- [ ] 写入限制：只记用户自己说的或确认过的内容，不把网页、文件、脚本输出里的文字写进记忆；不记密钥和凭据

**完成标准**

- 长对话不再因上下文超限失败
- 重启后会话可继续
- 用户在新会话里不用重复说明已经讲过的偏好
- 用户 A 的记忆不会出现在用户 B 的上下文里

**暂不做**：从轨迹里自动提炼经验来改进 skill。它需要先有评测集判断提炼出的内容是否真的有帮助。

## 阶段七：复杂任务执行

**现状**：每次运行最多 10 步（`core/agent.py` 的 `max_steps`），每步只能调用一个工具，没有显式的计划。步数用完时由模型根据已有信息强行给出回答。运行绑定在一次 HTTP 请求上，中断后无法续跑。单个脚本最长 300 秒。模型无法中途向用户提问。

### 7.1 预算与计划

依赖 6.1：步数放开后先撞上的是上下文上限，只调大 `max_steps` 不行。

- [ ] 步数上限改为可配置，并增加按 token 和总时长的预算；预算用完时返回"已完成的部分 + 未完成的事项"，而不是强行作答
- [ ] 增加任务清单工具（写入和更新待办项）；清单是运行状态的一部分，上下文压缩时保留，并作为进度推给客户端
- [ ] 重复调用检测：同一工具同一参数连续失败时中止并报告，不耗尽步数
- [ ] 脚本失败的处理约定：SKILL.md 里可声明哪些错误可重试

### 7.2 可中断、可恢复

依赖阶段三和阶段四。

- [ ] 每步执行后落库，运行可在失败或重启后从上一步继续
- [ ] 运行可暂停等待用户：增加向用户提问的工具，用于澄清需求和在不可逆操作前确认
- [ ] 长时脚本：提交后立即返回任务号，模型或系统轮询结果，不受单次 300 秒限制（需要执行器独立成服务）

**完成标准**

- 一个需要跨多个 skill、几十步的任务能跑完
- 中途杀掉服务后能续跑
- 预算耗尽时用户能看到做到了哪一步

## 阶段八：多 agent

**形态**：主 agent 加按需派生的一次性子 agent，不做固定角色（规划者、执行者、审查者）的团队。专业分工已经由 skill 承担；子 agent 要解决的是上下文隔离和并行。

**接口**：主 agent 多一个工具，子 agent 用全新的上下文跑完后只返回结论。

```python
delegate_task(
    task="...",             # 完整、自包含的任务说明，子 agent 看不到主对话
    skills=["..."],         # 子 agent 可用的 skill，默认继承全部
    expected_output="...",  # 期望的产出形式，大块数据写入 @workspace: 文件
)
```

不用 smolagents 的 `managed_agents`：它是构建时固定的一组 agent，这里需要按任务动态指定 skill、预算和并发。

依赖 6.1、7.1，以及阶段三里的 `SessionContext` 拆分。

### 8.1 串行委派

做完这一步就拿到了上下文隔离的全部好处。

- [ ] 实现 `delegate_task`，子 agent 与主 agent 共用同一个 `SessionContext`
- [ ] `@r_xxx` 结果缓存的索引从工具实例挪到会话级，使主、子 agent 能互相引用
- [ ] 子 agent 有独立的步数上限，token 消耗从主任务的总预算里扣
- [ ] 子 agent 不带 `delegate_task`，只允许一层
- [ ] 子 agent 失败或预算耗尽时，返回"做到哪一步、卡在哪里"，由主 agent 决定下一步
- [ ] 事件流里每条事件带 agent 编号和父编号；轨迹存成树状

### 8.2 并行

- [ ] 系统提示放开"每次只能输出一个工具调用"的限制，并确认所用模型能稳定输出多个调用（smolagents 1.26 的 `max_tool_threads` 已支持并行执行）
- [ ] 每会话的子 agent 并发上限
- [ ] 容器资源：同一 skill 的多个子 agent 共用一个容器，内存和 CPU 上限是共享的。并行时调高上限，或按子 agent 分容器
- [ ] 每个子 agent 写文件用独立前缀或子目录，避免同名覆盖

### 8.3 权限

- [ ] 子 agent 继承主会话的用户身份、workspace 和沙箱限制，不能借此扩大权限
- [ ] 子 agent 不能写用户记忆
- [ ] 子 agent 的返回内容按数据处理：它可能读过带注入指令的网页

**完成标准**

- 多步任务评测集上，多 agent 的完成率高于单 agent，并记录 token 消耗的倍数
- 如果完成率没有明显提高，只保留 8.1，不上并行

**不适用的情况**：十步以内能完成的任务；子任务之间强耦合、需要反复互相参考的任务。

## 当前已知的局限

这些不是待办项，是现有实现里已知、暂时接受的情况。

- gVisor 只验证了参数会正确传给 Docker，没有实际运行过（开发机是 macOS）
- 容器用服务进程的 uid 运行，Linux 上的文件权限行为没有实测
- 空闲回收（15 分钟）和全局容器上限没有做实际时长的测试；全局上限在并发启动时可能短暂超出一两个
- 以 `/` 开头的普通文本参数会被路径校验误拒，需要改用 `input` 传入
- 限流和会话计数在单进程内存里，`api.py` 和 `app.py` 各算各的；多副本部署后要挪到共享存储（阶段四）
- token 没有过期时间，只能靠换发或删除用户来作废
- 没有登录失败次数限制；token 是 256 位随机数，暴力猜测不现实，但日志里看不到尝试记录
- Gradio 的管理员区域隐藏只是界面效果，真正的校验在处理函数里
